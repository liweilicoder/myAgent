# 关于业务逻辑层重构的回复
## 1. 结论
**建议推进业务逻辑层重构，但需先补充数据模型层测试至 90%+，并建立分层解耦策略再启动。** 85% 覆盖率作为继续重构的"踏脚石"略有不足,尤其是边界场景(异常路径、并发、空值处理)的覆盖往往决定了下层重构的稳定性。
## 2. 依据
| 依据来源 | 内容 |
|---------|------|
| 📓 通用重构实践 | 在测试覆盖 < 90% 时进行上层重构,容易因下层边缘行为未验证而导致业务逻辑测试失真 |
| 📓 分层依赖关系 | 业务逻辑层通常强依赖数据模型层,模型层若有未覆盖的隐式行为,会污染业务层验证 |
| 📓 重构风险传导 | 业务层是系统的"语义中枢",回归成本高于模型层,需更强的测试网兜底 |

## 3. 风险与假设
**风险:**
- 🔴 **测试基线风险**:85% 覆盖率下重构业务层,若模型层缺陷暴露,定位成本会翻倍(需在两层间排查)
- 🟡 **接口稳定性风险**:模型层重构后接口是否已稳定?业务层重构假设模型层 API 冻结,否则会陷入循环重构
- 🟡 **依赖耦合风险**:若业务层与模型层耦合过紧(如直接持有 ORM 对象),重构会反向破坏已完成的工作
**假设:**
- 数据模型层 API 已稳定,不再有破坏性变更
- 团队对"业务逻辑层"的范围有共识(领域服务 / 应用服务 / 用例编排器)
- 已有 CI 流水线可在 PR 级别运行测试
