# 业务逻辑层重构推进建议
## 1. 结论
**可以启动业务逻辑层重构,但建议先补齐数据模型层剩余 15% 测试覆盖,再采用"绞杀者模式(Strangler Fig Pattern)"分模块渐进重构,而非一次性重写。** 当前 85% 覆盖率已具备重构安全网的基本条件,但尚未达到理想阈值(建议 ≥90%)。

## 3. 风险与假设
**主要风险:**
- 🚨 **测试覆盖不足风险**:15% 未覆盖代码可能包含边界条件和异常路径,业务逻辑层重构会暴露这些隐藏缺陷
- 🚨 **依赖蔓延风险**:业务逻辑层通常耦合度高于数据层,直接重构易引发大面积回归
- 🚨 **行为变更风险**:业务规则的隐式约定(如调用顺序、状态机)可能在重构中丢失
**关键假设:**
- 假设现有 85% 测试是有效的(非仅覆盖行数,包含断言质量)
- 假设业务逻辑层有清晰的边界划分(否则需先做领域分析)
- 假设团队有足够时间分阶段交付,而非一次性上线
## 4. 下一步行动建议
### 🎯 立即执行(本周)
1. **补充测试覆盖**:将数据模型层覆盖率提升至 90%+,重点覆盖异常路径
2. **梳理业务逻辑层技术债**:列出"代码异味"(God Class、长函数、重复逻辑)
3. **识别高价值模块**:按"修改频率 × 复杂度"排序,优先重构痛点模块
### 📋 短期计划(2-3 周)
4. **建立领域模型边界**:采用 DDD 战术模式(聚合、值对象、领域服务)划分模块
5. **选定试点模块**:挑选 1 个相对独立、价值高的模块作为试点
6. **制定绞杀者适配层**:新旧逻辑并存,通过 Facade 模式逐步切换
### 🛡️ 防护措施
7. **契约测试**:为业务逻辑层与外部依赖(数据层、外部服务)建立契约测试
8. **特性开关(Feature Flag)**:新逻辑通过开关控制,出问题可秒级回滚
9. **监控埋点**:在重构前后对关键业务指标(成功率、延迟)建立基线
